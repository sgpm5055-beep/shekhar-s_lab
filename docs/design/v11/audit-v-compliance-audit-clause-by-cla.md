# Audit: v1.1 compliance audit: clause-by-clause PRD coverage (sections 1-12, every FIXED rule, code value, required test, acceptance bullet) across the three delta designs plus the surviving v1.0 dossier pieces they reuse, with deep checks on reversed NTC, quota counting, report window, model-number invariant, confidence, LLM retry, consent-per-pull, locks, recompute/attach, pyright; plus feasibility spot-checks (supabase-py Storage, pyright strict + Pydantic v2 + Protocol, checkpointer/tracing reuse)

Finding counts: {'blocker': 3, 'major': 6, 'minor': 6}

## [blocker] pending_verification status x code (PRD 5.12, 6, 7)
**Issue:** Cross-design contradiction that cannot run: design 3's failure matrix and test 18 pin the bureau-timeout outcome as status='pending_verification' with code='SUREPASS_FAILURE', while design 1's checks.code_legality SQL CHECK and code_legal() predicate require code IS NULL for pending_verification, and design 2's bureau_pull node also writes code null. As integrated, either the persist insert/update violates the DB CHECK constraint at runtime or design 3's pinned test fails; the three artifacts cannot all be satisfied.
**Fix:** Adopt the 2-of-3 (and PRD-consistent) reading: pending_verification carries code=null (the §6 code list has no pending code; PAN_LOCKED is reserved for subsequent requests). Re-pin design 3's test 18 and failure-matrix row to code=null, keep MSG_PENDING_VERIFICATION in label, and keep build_failure_lc_view's status Literal accepting code=None for this status.

## [blocker] Timeout reconciliation gate (FIXED PRD 5.12)
**Issue:** Design 3's test 18 pins 'clock.advance(11min) -> lock expired, retry admitted', i.e. a billed re-pull is admitted after the 10-minute lock with no manual reconciliation — this violates FIXED rule 5.12 ('require manual reconciliation against the SurePass console before any re-pull') and directly contradicts design 1's reconciliation gate (unresolved review_queue kind='timeout_reconciliation' keeps refusing PAN_LOCKED via QK7/FL6 until resolved). Design 2's bureau_pull timeout path compounds it: it creates the 10-min lock but omits the timeout_reconciliation review row that design 1's binding node contract mandates.
**Fix:** Bureau timeout must write BOTH the 10-min timeout lock AND an unresolved review_queue row kind='timeout_reconciliation' (add to design 2's bureau_pull spec); admission keeps refusing billed pulls on that pan_hash after lock expiry while the review row is unresolved. Re-pin design 3's test 18: retry at +11min still refused PAN_LOCKED; add repo.resolve_review(...) then retry admitted.

## [blocker] HMAC hashing single home (PRD 5.2)
**Issue:** Two mutually exclusive 'single homes' for the FIXED HMAC-SHA256 identity hashing: design 1 puts normalize/hash_pan/hash_mobile in policy/guards.py with env IDENTITY_HMAC_KEY and domain-separated messages (b'pan:'+PAN, b'mobile:'+MOBILE; pinned vector 7c0b91b0...), while design 3 puts hash_pii/hash_pan/hash_mobile in config.py with env PII_HMAC_KEY and NO domain separation (pinned vector hmac(key, b'ABCDE1234F')), and its conftest sets PII_HMAC_KEY. Both claim 'everyone imports, no second definition anywhere'. The two pinned test vectors are mutually exclusive, and every cache row, lock, consent, quota and PAN-correction record keys on this hash — the combined suite cannot go green and a split implementation would fracture the cache keyspace.
**Fix:** Pick exactly one: recommend design 1's version (policy/guards.py, domain-separated — strictly stronger, matches the delta brief's module assignment), one env name (IDENTITY_HMAC_KEY). Update design 3's config env table, conftest pytest_configure, helpers, and hash test vectors to import from policy/guards; config.py keeps only the env field.

## [major] Display rounding of ceiling/range (PRD 8.4, 12 numbers_from_code)
**Issue:** Design 2 (derive/range owner) specifies floor_to_1000 applied inside the range node ('never overstates'; 222,749.10→222,000; 'v1.0 half-up NOT binding'), while design 3 specifies round_to_nearest_1000 half-up applied at redact and claims its single home is derive/range.py (367,536.02→368,000; 328,554.93→329,000; 294,502.64→295,000; 731,500→732,000). The pinned test constants diverge on at least three values, the helper name and the call site differ, and the numbers_from_code evaluator compares exact equality between view and derived values — the integrated test suite and CI evaluators cannot both pass.
**Fix:** One helper, one home, one call site: put the chosen rounding function in derive/range.py, applied once (either in LenderNumbers or in build_lc_view, not both), and regenerate the losing design's pinned constants. Owner should pick floor (learner-protective, design 2's rationale) or half-up (v1.0 precedent, design 3); either satisfies the PRD, which specifies no rounding.

## [major] OPENAI_FAILURE wire shape (PRD 6 vs 7/12 — flagged contradiction resolved oppositely)
**Issue:** Both designs correctly flag the PRD self-contradiction (§6 'top_lender and alternates are null/empty when confidence is low' vs §7/§12 'OPENAI_FAILURE ... band read + gated list still shown/returned'), but resolve it in OPPOSITE directions: design 2's D-OPENAI populates alternates with up to two code-built, number-free gated-lender entries; design 3's decision and test 17 pin top=None, alternates=[] with the gated list in checks.internal only. Design 3's reading fails the letter of the §12 required test ('gated list still returned'); the two pinned test expectations conflict.
**Fix:** Owner adjudication required; default to design 2's D-OPENAI (satisfies the §12 required-test letter: code-built alternates without numbers, canned rationale, confidence low, review row). Re-pin design 3's test 17, the failure matrix row, and the build_lc_view low-confidence exception to match, and exempt this one path in the low-confidence-nulls rule.

## [major] Quota counting on OPENAI_FAILURE quick runs (PRD 5.6)
**Issue:** Designs disagree on whether a quick run whose Score call succeeded (billed, 200+success:true, no stored score) but whose rank node then failed twice counts against the quota: design 1's compute_counted_against_quota and design 3's test 17 ('billed True counted True') count it, but design 2's persist formula gates on status in (None,'ok') and OPENAI_FAILURE persists as service_failure — so it would NOT count. PRD 5.6's 'does not count: ... any service failure' is ambiguous about whether a downstream OpenAI failure (vs a bureau service failure) exempts the already-billed Score pull.
**Fix:** Make design 2's persist node call design 1's compute_counted_against_quota(kind, counts_against_quota, calls) verbatim (single formula; counts whenever a 200+success Score row exists), delete the status-gate variant, and surface the 5.6 'service failure' scope question to the owner as a flagged interpretation (counting is the cost-conservative reading since the spend happened).

## [major] Recompute persistence lineage (PRD 6 recompute)
**Issue:** Design 2's recompute graph updates the SAME checks row ('persist updates the existing checks row with the new lc_view'; 'finish_check updates the SAME row') while designs 1 (R5: new row with recompute_of column, billed=False, counted=False, from_cache=True) and 3 ('success creates a NEW checks row ... internal.recompute_of') create a new row. Under design 1's terminal-guarded update_check (patches apply only while status=='running'), design 2's same-row update silently no-ops against a terminal row — recompute results would never persist; reusing the original check_id as thread_id also collides with the original run's checkpoints.
**Fix:** Standardize on new-row semantics: recompute mints a new check_id (new checkpointer thread), inserts status='running' with recompute_of=<original> (design 1's column, not just internal), then one guarded terminal update. Amend design 2's build_recompute_graph docstring and persist node; design 3's internal.recompute_of moves to the column.

## [major] Repo interface + cache-row shape consumed by graph nodes (PRD 5.4; VOID v1.0 derived-jsonb)
**Issue:** Design 2's node contract consumes a Repo that design 1 does not provide and partially resurrects the VOID v1.0 derived-jsonb contract: pan node reads pan_records.derived and calls put_pan_record(..., derived=identity.model_dump(...)); quick-reuse reads get_score_cache(pan_hash) -> ScoreFacts directly (design 1's ScoreCacheRow carries storage_key/is_ntc only, no facts); nodes call store_raw(), insert_surepass_call(6-arg), finish_check(), insert_review_queue(), lock_pan() where design 1 provides fetch_raw(), log_surepass_call(10-arg sink that owns the raw upload), update_check(patch), insert_review_item(row), create_pan_lock(). Design 2 is also internally inconsistent — its full-reuse path re-adapts stored raw 'so derivations always run on current adapter code' while its pan/score reuse paths use stored derived, which is exactly what PRD 5.4 and design 1's caches-store-pointers decision forbid freezing.
**Fix:** Graph nodes must consume Repo protocol v2 exactly: every reuse path (pan, score, report) = repo.fetch_raw(row.storage_key) + re-run the adapter; no derived columns anywhere; rename node calls to log_surepass_call/update_check/insert_review_item/create_pan_lock/release_pan_lock; drop store_raw (the sink uploads). Update design 2's nodes.py contract and its interfaces_consumed db.repo block wholesale.

## [major] Admission guard architecture (PRD 5/7 seam)
**Issue:** Design 2's admission node calls an impure policy.guards.admit(kind, repo, ..., consent, live_enabled, now) -> AdmissionFacts that itself writes the consent row and acquires locks, while design 1 provides pure decision tables admit_quick(facts)/admit_full(facts, full) over a pre-fetched AdmissionFacts snapshot returning an AdmissionDecision, with the NODE executing the 8-step write order. Worse, the name 'AdmissionFacts' denotes the INPUT snapshot (pan_row/score_row/quota_used...) in design 1 but the OUTPUT decision (mode_pan/mode_bureau/refusal_code/consent_id...) in design 2's state.py — two different shapes under one name, with non-matching fields (pan_plan vs mode_pan; design 2's shape lacks the directive fields create_daily_cap_lock/review_reason the node must execute).
**Fix:** Adopt design 1's split (it is the policy owner and keeps TOCTOU-sensitive lock acquisition in the node with pure, table-testable guards): design 2's admission node implements the 8-step order verbatim and calls admit_quick/admit_full; rename design 2's state model to AdmissionOutcome mapping 1:1 onto AdmissionDecision fields (pan_plan, bureau_plan, counts_against_quota, is_refresh, checked_on, refresh_available_on, original_consent_id) plus consent_id captured by the node.

## [minor] Design 1 admission write order vs C1 insert-early
**Issue:** Design 1's own 8-step order inserts the checks row at step 4, AFTER existing-lock checks (step 2) and in-flight acquisition (step 3), yet C1 (cited as surviving) requires the row 'for EVERY outcome incl. refusals'. IN_FLIGHT, PAN_LOCKED and existing-daily-cap refusals fire at steps 2-3 with no running row, so persist_refusal's guarded update_check has nothing to update and the refusal is unauditable as a checks row.
**Fix:** Either move insert_check before the lock checks (step 1.5) — the FK comment only requires it before SurePass calls — or specify that persist_refusal inserts the refused row directly (record_check_error-style insert-if-absent) for pre-insert refusal codes; pin one behavior and add a test asserting an IN_FLIGHT refusal leaves a checks row.

## [minor] opportunity_stage handling (PRD 5.8)
**Issue:** Design 3 validates opportunity_stage as an OpportunityStage enum (unknown string -> 422, per surviving C18) while design 1 types CheckRow.opportunity_stage as str|None stored verbatim with unknown failing closed to STAGE_TOO_EARLY; PRD 5.8 says the service 'trusts it and logs it'. ## [minor] LcView module home vs strict-msgpack allowlist (reused C15)

## [minor] billed-on-timeout and billing_consistency evaluator precision
**Issue:** Design 1 pins billable := (200 AND success) OR error_kind=='timeout' so a timed-out check persists billed=true (conservative, reconciliation corrects), while design 3's failure matrix marks the timed-out run's billed flag 'unknown -> internal.spend_unknown=true' and defers to reconciliation. Separately, design 3's billing_consistency evaluator asserts billed == (len(call_endpoints) > 0), which is false for a run whose only call row is a non-billable validation-failure envelope (billable=False under design 1) — the evaluator would flag a correct run.
**Fix:** Standardize on design 1's billable predicate (checks.billed = any billable row; keep internal.spend_unknown for ops) and re-state design 3's matrix row; change the evaluator to billed == any(call is billable) using the same predicate semantics (expose per-call billable in the eval outputs contract) rather than call-count.
